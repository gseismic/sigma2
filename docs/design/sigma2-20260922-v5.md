## 1. v5 核心结论

sigma2 是面向市场数据的有状态信号库，不是 pyta2 的包装器集合，也不是以 FeatureSet、DAG 或 DataFrame 为核心的应用框架。

v5 冻结以下方向：

1. `rSignal` 是核心开发接口；一个具体信号是最小稳定单元。
2. `step()` 每次接收一条新的逻辑观测并推进状态。
3. `update_last()` 修订最后一条逻辑观测，不推进时间索引。
4. `rSignal` 不固定 OHLCV；输入契约由 `kline`、`orderbook`、`trade` 等 family 定义。
5. pyta2 提供成熟的 rolling 指标、schema、full name、窗口元信息和状态更新能力。
6. sigma2 不复制 pyta2 的 schema、full name、指标定义或 registry。
7. pyta2 指标直接转成 Signal 只需要一个薄桥接器，不为每个 pyta2 指标创建一套 `rPyta2Xxx` 包装类。
8. sigma2 的主要价值是使用 pyta2 指标、市场结构逻辑和自定义状态，定义更高层、更复杂、更有数据语义的信号。
9. 每个公开信号原则上独立文件，像 pyta2 一样可发现、可阅读、可测试、可继承。
10. 源码第一层继续按输入数据 family 分类；算法分类只能作为 family 内的第二层分类。
11. batch、研究数据集、因子分析、模型训练和交易模拟消费 Signal，但不定义 Signal core。

一句话定位：

```text
pyta2 提供计算积木；sigma2 把市场事件、计算积木和业务逻辑组合成可持续运行的信号。
```

## 2. 版本演化

### v2：FeatureSpec-first

v2 以 `IndicatorDef + FeatureSpec + FeatureEngine` 为中心，重点处理字段绑定、共享 buffer 和批量特征矩阵。

主要问题：

- 把指标定义重复写入 sigma。
- 信号类不是一等公民。
- 普通自定义信号需要先学习声明系统。

### v3：pyta2 元信息作为事实来源

v3 确认 pyta2 已经拥有：

- `schema`
- `output_keys`
- `window`
- `extra_window`
- `required_window`
- `full_name`
- `meta_info`
- `rolling()`

因此 sigma 不应再维护完整 `IndicatorDef`。

但 v3 仍然偏向 FeatureSpec、FeatureGraph 和 FeatureEngine。

### v4：rSignal-first（2026-07）

上一版 sigma2 总设计把核心收敛为：

- `rSignal`
- family 基类
- `step()`
- 一个信号一个文件

该方向保留。v5 主要修正以下内容：

- 增加 `update_last()`。
- 明确 pyta2 只需要单一薄桥接器。
- 不再建设与 pyta2 平行的 primitive catalogue。
- 把“使用 pyta2 组合复杂信号”提升为 sigma2 的核心能力。
- 明确 family、具体信号和应用层之间的长期边界。

## 3. 目标与非目标

### 3.1 设计目标

sigma2 应支持以下高频场景，优先级从高到低排列：

1. 用户继承 family 基类，在单独文件中实现一个自定义信号。
2. 一个 K 线信号组合多个 pyta2 指标，例如均值的均值、波动率过滤动量、ATR 标准化突破。
3. 一个 orderbook 信号从 bids/asks 提取价差、深度、失衡度，再使用 rolling 统计量。
4. 一个 trade 信号从逐笔成交形成主动买卖流、成交强度或滚动冲击指标。
5. 实时运行时，每个新事件调用 `step()`，当前未完成事件修订调用 `update_last()`。
6. 离线 runner 逐条重放 finalized data，得到与在线 `step()` 一致的结果。
7. 多 symbol、多 venue 场景为每条数据流创建独立 Signal 实例。
8. 研究训练层将 Signal 输出收集为 FeatureData、TargetData 和 ResearchDataset。
9. 高级用户临时把一个原生 pyta2 指标直接桥接为 Signal，而不创建新的包装类。
10. 新增 market-data family 时，不修改既有 family 的公共输入契约。

### 3.2 非目标

sigma2 core 不负责：

- 复制 pyta2 指标目录或完整指标 registry。
- 为每个 pyta2 类生成 `rPyta2SMA`、`rPyta2EMA`、`rPyta2MACD` 等镜像类。
- 重写 pyta2 已有 schema、Space、Deque 或 rolling 状态机。
- 以通用 DAG、表达式 DSL 或 FeatureSpec 作为普通用户的第一入口。
- 在 core 中依赖 pandas、polars、torch、minbt 或交易所 SDK。
- 在 Signal 内判断时间戳属于新 bar 还是当前 bar。
- 修改任意历史位置；`update_last()` 只修订最后一个逻辑观测。
- 把 kline 输入强加给 orderbook、trade 或未来 family。
- 在第一阶段实现自动模型训练、完整回测器或 RL 环境。

## 4. 系统边界

### 4.1 pyta2

pyta2 是基础 rolling 计算库，负责：

- 通用技术指标与统计指标。
- 指标自己的 rolling 计算状态。
- `rolling()` 与 `update_last()` 生命周期。
- `schema`、`output_keys`、`full_name`、`meta_info`。
- `window`、`extra_window`、`required_window`。
- 指标 registry 和指标发现。
- `NumpyDeque`、`DequeTable` 等底层工具。

pyta2 不需要知道：

- 一个 `values` 参数来自 `kline.close`、盘口 mid price 还是成交 price。
- symbol、venue、event time 或 bar identity。
- 一个指标在研究中被称为什么 feature。
- 多个市场事件 family 如何标准化。

### 4.2 sigma2 core

sigma2 core 负责：

- `rSignal` 生命周期。
- `step()`、`update_last()`、`reset()`。
- Signal 输出缓存与 schema 契约。
- family 输入契约。
- Signal 自身计算状态的检查点与恢复。
- 在 Signal 生命周期中正确调用 pyta2 子指标。
- 供 runner 消费的最小协议和元信息。

### 4.3 具体信号目录

`sigma2.kline`、`sigma2.orderbook`、`sigma2.trade` 等目录负责：

- 公开的具体信号类。
- 从 family 输入提取本信号真正需要的值。
- 组合 pyta2 指标与自定义逻辑。
- 定义新信号自己的 schema、full name 和 warmup。
- 一个公开信号一个文件。

### 4.4 research / application 层

应用层负责：

- DataFrame、Arrow、NumPy 等批量输入适配。
- symbol/venue 分流和 Signal factory。
- 决定调用 `step()` 还是 `update_last()`。
- FeatureData、TargetData、ResearchDataset。
- IC、RankIC、分组收益和模型训练。
- 在线 pipeline、交易模拟和外部框架 bridge。

应用层只能调用 Signal 公共生命周期，不能直接调用 `forward()`。

## 5. 核心概念

v5 尽量只保留五个核心概念：

| 概念 | 作用 | 稳定性 |
| --- | --- | --- |
| `rSignal` | 有状态信号生命周期与输出契约 | 最先冻结 |
| Signal family | 定义一条市场观测的输入结构 | 按 family 冻结 |
| Concrete Signal | 具体可运行、可发现的信号 | 逐个稳定 |
| Pyta2 bridge | 将 pyta2 指标接入 Signal 生命周期 | 单一薄层 |
| Signal runner | 为数据流管理实例并收集输出 | core 之后稳定 |

不把以下概念放入 core 主路径：

- FeatureSpec
- FeatureGraph
- IndicatorDef
- DataFrame schema
- Model pipeline
- Backtest strategy

## 6. 用户接口方案比较

### 6.1 方案 A：pyta2 adapter catalogue

```python
rPyta2SMA(...)
rPyta2EMA(...)
rPyta2MACD(...)
```

优点：

- 上手直观。
- 每个包装类可以固定字段绑定。

缺点：

- 与 pyta2 一对一重复。
- pyta2 新增或修改指标时，sigma2 需要同步维护。
- sigma2 容易退化成 pyta2 镜像包。
- 大量包装类并没有增加新的信号语义。

结论：不采用为主模式。不再扩展 `rPyta2Xxx` catalogue。

### 6.2 方案 B：FeatureGraph / DSL-first

```python
signal = SMA(SMA(Field("kline.close"), 5), 20)
```

优点：

- 动态组合能力强。
- 容易序列化和批量搜索参数。

缺点：

- 生命周期、调试、类型、错误定位和自定义状态复杂。
- orderbook/trade 的结构化逻辑很快突破纯表达式模型。
- 一个复杂信号的业务语义容易埋在匿名图中。
- 简单的自定义类反而需要先理解 DSL。

结论：可作为未来实验层，不能定义 core。

### 6.3 方案 C：独立 Signal 类 + 单一 pyta2 bridge

```python
class rMeanOfMean(rKlineWindowSignal):
    ...
```

每个信号：

- 有独立类。
- 有独立文件。
- 可以组合任意数量 pyta2 指标。
- 可以混入自定义市场逻辑。
- 有清晰 schema、full name、测试和生命周期。

直接使用单个 pyta2 指标时走同一个通用 bridge。

优点：

- 信号是稳定、可阅读、可 review 的代码单元。
- 不复制 pyta2 catalog。
- 复杂逻辑不受 DSL 限制。
- 与 kline、orderbook、trade family 自然结合。
- 可以逐信号优化性能和状态。

缺点：

- 文件数量较多。
- 参数搜索和序列化需要后续 SignalSpec/factory 补充。

结论：采用。

### 6.4 单条输入接口方案比较

`step()` 的输入形态还有三种可选方案。

方案 A：把历史数组直接传给 Signal：

```python
signal.step(opens, highs, lows, closes, volumes)
```

优点是接近 pyta2 `rolling()`；缺点是调用方与 Signal 同时管理窗口，无法清晰表达“新增一条观测”和“修订最后一条观测”，也容易让不同 runner 产生不同历史切片。该方案不采用。

方案 B：所有 family 统一接收 `MarketEvent` 或 mapping：

```python
signal.step(event)
```

优点是扩展字段容易；缺点是静态签名、类型提示、必填字段和错误定位变弱，K 线、盘口与成交的语义也被隐藏。它适合 adapter 层，不作为 Signal family 的主接口。

方案 C：每次接收一个 family 的单条观测，并由 family 给出显式签名：

```python
kline.step(open=..., high=..., low=..., close=..., volume=...)
trade.step(price=..., volume=..., side=...)
```

优点是 append/revise 语义清楚，输入契约可发现，Signal 自己拥有窗口。结论：采用。

公开 family 方法使用 keyword-only 参数，避免 OHLCV 等同类型参数发生静默错位；core 内部调用 `forward()` 时可以继续使用位置参数，不把关键字分派成本带入公式层。

## 7. rSignal 生命周期

### 7.1 公共接口

概念接口：

```python
class rSignal:
    name: str | None
    family: str | None
    step_input_keys: tuple[str, ...]

    def step(self, *args, **kwargs):
        """输入一个新的逻辑观测并推进状态。"""

    def update_last(self, *args, **kwargs):
        """使用新输入修订最后一个逻辑观测，不推进索引。"""

    def reset(self) -> None:
        ...

    def forward(self, *args, **kwargs):
        """子类计算 hook；不是 runner 的公共入库入口。"""
```

稳定字段继续包括：

- `window`
- `extra_window`
- `required_window`
- `schema`
- `output_keys`
- `outputs`
- `latest`
- `return_dict`
- `buffer_size`
- `buffer_factor`
- `name`
- `full_name`
- `family`
- `step_input_keys`
- `g_index`
- `meta_info`

稳定方法包括 `step()`、`update_last()`、`reset()`、`forward()`、`reset_extras()` 和 `make_dict_output()`；其中 `forward()` / `reset_extras()` 是 Signal 作者接口，不是 runner 入口。

### 7.2 step 语义

`step()` 接收的是一条新的逻辑观测，不是整个历史序列。

行为：

1. 在修改状态前完成参数形状和 family 必填字段校验。
2. 保存进入本观测之前的计算状态。
3. 将 `g_index` 临时置为候选下一索引，并将观测追加到 family 输入状态。
4. 执行 Signal 计算和输出 schema 校验。
5. 成功后提交 `g_index`，并将输出追加到 `outputs`。
6. 按 `return_dict` 返回结果。

如果第 4 步失败，公开的 `g_index` 和输出缓存保持在最近一次成功提交的位置，实例进入 faulted 状态；详见 11.4。

`step()` 是唯一推进到新逻辑观测的方法。

“新逻辑观测”不等于“已经最终确定”：实时 K 线可以在新 bar 首次出现时 `step()`，随后用 `update_last()` 持续修订，最终一次修订即为该 bar 的收盘状态。

### 7.3 update_last 语义

`update_last()` 与 `step()` 接收完全相同的输入结构，并返回相同格式。

行为：

1. 必须已有至少一次成功 `step()`；否则抛 `IndexError`。
2. 恢复到最近一次 `step()` 之前的计算状态。
3. 替换 family 输入状态中的最后一条观测。
4. 使用新输入重新计算当前观测。
5. `g_index` 不变。
6. `outputs` 行数不变，只覆盖最后一行。
7. 保留同一个观测前检查点，允许连续修订。

关键不变量：

```text
step(old_current)
-> update_last(final_current)
-> step(next)

等价于

step(final_current)
-> step(next)
```

`update_last()` 只表达“替换最后一条逻辑观测”，不表达：

- 任意历史修订。
- orderbook delta 应用。
- trade cancel/correction 协议。
- 自动 bar identity 判断。

这些语义由行情 adapter 或专门的 family 负责。

### 7.4 forward 语义

`forward()` 是二次开发 hook，不是用户或 runner 的状态入口。

准确契约：

- 不直接修改 core 管理的 `g_index`。
- 不直接写顶层 `outputs`。
- 不处理 `return_dict`。
- 不负责判断 append 还是 revise。
- 可以修改算法私有计算状态；递推指标不要求 `forward()` 是纯函数。

因此，直接调用 `forward()` 不保证得到一个可继续 `step()` 的完整生命周期状态。测试、runner 和应用层不得依赖直接调用 `forward()` 推进 Signal。

### 7.5 reset 语义

`reset()` 必须同时清除：

- `g_index`
- 输出缓存
- family 输入窗口
- Signal 私有计算状态
- 最近一次观测前检查点
- 嵌套组件的状态
- faulted 状态

`reset()` 后调用 `update_last()` 必须抛出 `IndexError`。

### 7.6 并发语义

- 一个 Signal 实例只属于一条输入流。
- Signal 实例不是线程安全对象。
- 多 symbol、多 venue、多周期必须使用独立实例。
- 跨线程共享需要调用方加锁，但推荐直接隔离实例。

### 7.7 生命周期状态机

```text
EMPTY   -- step 成功 ----------------> ACTIVE
EMPTY   -- update_last --------------> IndexError
ACTIVE  -- step / update_last 成功 --> ACTIVE
EMPTY/ACTIVE -- 状态计算失败 --------> FAULTED
FAULTED -- step / update_last --------> RuntimeError
ACTIVE/FAULTED -- reset -------------> EMPTY
```

直接调用 `forward()` 不属于该状态机，也不能建立可供 `update_last()` 使用的当前观测。

## 8. family 输入设计

### 8.1 通用原则

`rSignal` 不知道 OHLCV、盘口或成交字段。family 负责：

- 定义一条逻辑观测的输入键。
- 提供显式 `step()` / `update_last()` 签名。
- 管理必要的 family 输入窗口。
- 说明事件是 snapshot、delta 还是独立成交。

同一 family 的两个公共方法必须同签名：

```text
step(input)          -> append
update_last(input)   -> replace last
```

不采用：

```python
step(input, update=True)
step(input, mode="replace")
update(input)
```

原因是 boolean/mode 会隐藏状态操作，而 `update()` 在盘口语境中容易被理解为应用 delta。

### 8.2 K 线 family

```python
class rKlineSignal(rSignal):
    family = "kline"
    step_input_keys = ("open", "high", "low", "close", "volume")

    def step(self, *, open, high, low, close, volume):
        ...

    def update_last(self, *, open, high, low, close, volume):
        ...
```

约束：

- 公共输入是一根 K 线的标量字段。
- 不把历史 arrays 暴露给普通用户。
- `rKlineSignal` 不默认保存 OHLCV 历史。
- 需要历史数组的信号使用 `rKlineWindowSignal`。
- 时间戳、symbol 和 bar id 由 runner 管理，不进入最小计算签名。

`rKlineWindowSignal`：

```text
step()        -> _window.append(row)
update_last() -> _window.update_row(-1, row)
forward()     -> 接收当前窗口 arrays
```

### 8.3 orderbook family

第一批稳定 family 应区分 snapshot 和 delta。

快照：

```python
class rOrderBookSignal(rSignal):
    family = "orderbook"
    step_input_keys = ("bids", "asks")
```

语义：一条输入是完整盘口快照。

未来增量：

```python
class rOrderBookDeltaSignal(rSignal):
    family = "orderbook_delta"
```

两者不能共用一个含糊的 `update()`。

典型 sigma2 信号：

- spread
- mid price
- micro price
- depth imbalance
- rolling imbalance
- orderbook pressure
- liquidity slope

其中 rolling 统计部分可以复用 pyta2，盘口结构提取属于 sigma2。

### 8.4 trade family

```python
class rTradeSignal(rSignal):
    family = "trade"
    step_input_keys = ("price", "volume", "side")
```

一条输入是一笔独立成交事件。

典型 sigma2 信号：

- signed volume
- trade imbalance
- rolling VWAP deviation
- aggressor intensity
- trade arrival rate
- price impact

交易所的成交撤销或修正不是普通 `update_last()` 的替代语义；需要 adapter 将其转成“替换最后成交”或专门事件 family。

### 8.5 新 family

新增 funding、quote、liquidation、news 等 family 时：

1. 新增 family 基类。
2. 定义单条观测的明确输入结构。
3. 明确 snapshot/delta/event 语义。
4. 至少实现两个真实信号和 contract tests 后再冻结。
5. 不修改既有 family 的签名。

## 9. pyta2 单一桥接器

### 9.1 定位

pyta2 bridge 是一个边界适配器，不是 sigma2 的产品中心。

它只负责：

- 将 family 字段绑定到 pyta2 `forward()` 输入。
- 为已绑定的标量字段维护 pyta2 所需的有界历史数组。
- 将 Signal 的 append/revise 生命周期映射到 pyta2 `rolling()` / `update_last()`。
- 复用 pyta2 已有元信息。

它不负责：

- 重新声明 schema。
- 重新生成指标 full name。
- 复制 pyta2 registry。
- 维护一套 pyta2 参数定义。
- 为每个指标创建专属 wrapper class。

### 9.2 元信息委托

直接桥接一个 pyta2 指标时：

| Signal 信息 | 来源 |
| --- | --- |
| `schema` | `indicator.schema` |
| `output_keys` | `indicator.output_keys` |
| `window` | `indicator.window` |
| `extra_window` | `indicator.extra_window` |
| `required_window` | `indicator.required_window` |
| 算法 `full_name` | `indicator.full_name` |
| 算法 `meta_info` | `indicator.meta_info` |
| `family` | sigma2 binding |
| `bind` | sigma2 binding |
| `step_input_keys` | sigma2 family |

桥接器不得把上述 pyta2 信息重新硬编码一遍。

同一个 `rSMA(20)` 可以绑定到 close 或 volume。算法 full name 仍来自 pyta2；字段来源记录在独立 `bind` metadata 中。需要全局唯一列名时，runner 使用：

```text
family + bind + indicator.full_name + output_key
```

而不是要求 pyta2 知道市场字段。

### 9.3 建议接口

普通用户主要使用具体 sigma2 信号。直接桥接属于便捷/高级接口：

```python
from pyta2 import rSMA
from sigma2 import pyta2_signal

signal = pyta2_signal(
    rSMA(20),
    family="kline",
    bind={"values": "close"},
)
```

构造输入有三种方案：

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 传入 pyta2 实例 | 最薄；立即复用真实 schema/full name/window | 必须明确实例所有权 | 主接口 |
| 传入 class + params | 兼容当前 API | 重复一套构造协议 | 仅保留一个 minor 的 deprecated 重载 |
| 传入 factory | 可延迟构造 | lambda 不可稳定序列化；所有权更隐晦 | 第一阶段不采用 |
| 传入字符串名 | 配置友好 | 仍需参数构造；容易诱发 sigma2 私有 registry | 仅兼容入口，必须委托 pyta2 registry |

设计要求：

- `pyta2_signal()` 是唯一推荐的公开桥接构造器；实现可以使用私有 family driver，但不得形成公开的逐指标 wrapper 体系。
- 第一阶段只接受具有有限正整数 `required_window` 的 pyta2 `rIndicator` 实例；`rEffect`、future outcome 和无状态函数不走这个 bridge。
- 传入的 pyta2 实例必须尚未推进，即 `g_index == -1`；否则拒绝构造，避免 bridge 历史与指标状态错位。
- bridge 取得该实例的独占所有权；同一个 pyta2 实例不得交给两个 Signal，也不得再由外部调用。
- `reset()` 直接调用该实例的 `reset()`，不克隆、不反射重建指标。
- bridge 从这个实例读取 schema 和元信息，且计算只调用它的公共 API。
- bridge 接管后通过 pyta2 公共 `resize_buffer(0)` 关闭子指标输出缓存；结果历史只由 Signal 缓存，避免双份所有权。
- `bind` 左侧是 pyta2 输入名，右侧是 family 字段名。
- 左侧输入名以 pyta2 `forward()` 的公开签名为准；bridge 用关键字调用，不依赖 mapping 插入顺序。
- bridge 校验所有 pyta2 必需输入均已绑定，且不存在未知的 pyta2 输入名。
- bridge 校验绑定目标属于 family 输入字段。
- v5 第一阶段只支持“pyta2 输入名 -> family 直接标量数值字段”的静态绑定，不接受匿名 extractor、表达式、结构化盘口字段或隐式派生字段。
- 因此首版最适合 kline 数值字段和 trade 的 price/volume；原始 orderbook bids/asks 通常必须先进入 concrete Signal 派生标量。
- 需要 mid price、micro price、signed flow 等派生值时，应建立独立 concrete Signal，在 Signal 内显式计算后再调用 pyta2。
- 字符串指标名如果支持，必须委托 pyta2 registry，不建立 sigma2 私有 registry。

精确构造签名在首次实现前仍可做小范围调整，但以上语义属于 v5 稳定设计。

### 9.4 生命周期映射

```text
Signal.step(event)
    -> 提取 bind 对应的单个标量
    -> 追加到 bridge 自己的绑定字段历史
    -> indicator.rolling(**历史数组)
    -> Signal output append

Signal.update_last(event)
    -> 替换绑定字段历史的最后一个标量
    -> indicator.update_last(**修订后的历史数组)
    -> Signal output replace-last
```

bridge 的输入历史规则：

- 每个被绑定的 family 字段只维护一份历史，最大长度为 `indicator.required_window`。
- 同一 family 字段绑定到多个 pyta2 输入时共享该历史。
- 传给 pyta2 的是从旧到新的数组，不是当前事件标量。
- bridge 只保存被绑定字段，不复制完整 kline、orderbook 或 trade 事件。
- `update_last()` 只替换各绑定历史的末项，连续修订不增加长度。
- 这些历史属于 Signal 的 family/input 状态，进入父 Signal 的检查点协议；pyta2 实例自身仍通过其 `update_last()` 恢复。

bridge 只能调用 pyta2 公共方法，不依赖：

- `_snapshot_update_state()`
- `_restore_update_state()`
- `_pre_bar_state`
- pyta2 私有 ContextVar

### 9.5 兼容命名

当前 `rPyta2Signal` 可以在迁移期作为这个单一 bridge 的兼容公开名。

长期不再新增：

```text
rPyta2SMA
rPyta2EMA
rPyta2ATR
rPyta2MACD
...
```

已有 `rPyta2SMA` 在一个 minor 版本内保留，并改为调用通用 bridge；文档停止推荐，之后再移除。

## 10. 使用 pyta2 定义复杂 Signal

### 10.1 原则

复杂 Signal 是 sigma2 的核心价值，而不是 bridge 的特例。

一个具体 Signal 可以组合：

- 一个或多个 pyta2 指标。
- 一个或多个 pyta2 无状态函数。
- family 原始字段。
- family 派生字段。
- 自定义标量或容器状态。
- 条件、过滤、归一化和市场结构规则。

组合结果是一个新的 Signal，因此由该 Signal 自主定义：

- 业务名称。
- 输出 schema。
- full name。
- required window。
- family。
- 参数和 metadata。

子 pyta2 指标的 schema/full name 只作为 component metadata，不直接替代组合 Signal 的公共语义。

有状态 `rIndicator` 必须通过 `_apply_pyta2()` 进入 append/revise 生命周期；纯函数没有需要回滚的内部状态，可以在 `forward()` 中直接调用。纯函数通常也没有完整 Signal schema/full name，因此不进入直接 bridge。

### 10.2 均值的均值示例

推荐文件：

```text
sigma2/kline/mean_of_mean.py
```

概念代码：

```python
from pyta2 import rSMA
from pyta2.utils.deque import NumpyDeque
from pyta2.utils.space import Scalar


class rMeanOfMean(rKlineWindowSignal):
    name = "mean_of_mean"
    _update_state_fields = ("_inner_values",)

    def __init__(self, inner_n: int, outer_n: int, *, field="close", **kwargs):
        self.inner_n = inner_n
        self.outer_n = outer_n
        self.field = field

        self._inner = rSMA(inner_n, buffer_size=0)
        self._outer = rSMA(outer_n, buffer_size=0)
        self._inner_values = NumpyDeque(maxlen=outer_n)

        super().__init__(
            window=inner_n + outer_n - 1,
            schema={"mean_of_mean": Scalar()},
            **kwargs,
        )

    def reset_window_extras(self):
        self._inner.reset()
        self._outer.reset()
        self._inner_values.clear()

    def forward(self, opens, highs, lows, closes, volumes):
        values = self._select_field(opens, highs, lows, closes, volumes)
        inner = self._apply_pyta2(self._inner, values)
        self._inner_values.append(inner)
        return self._apply_pyta2(self._outer, self._inner_values.values)

    @property
    def full_name(self):
        return (
            f"mean_of_mean({self.field},"
            f"inner={self.inner_n},outer={self.outer_n})"
        )
```

说明：

- 这是一个 sigma2 信号，不命名为 `rPyta2SMAOfSMA`。
- schema 属于新的组合输出。
- `required_window = inner_n + outer_n - 1`，表示原始 family 观测的真实 warmup。
- pyta2 子指标只承担均值计算与自身状态。
- `_apply_pyta2()` 是 core 提供的受保护生命周期桥接 hook；正常 step 调用 `rolling()`，当前观测修订调用 `update_last()`。
- `_inner_values` 是 Signal 自己的中间状态，进入父 Signal 检查点；`_inner`、`_outer` 由各自 pyta2 生命周期管理。
- `reset_window_extras()` 必须同时重置所有子指标和中间缓存，保证显式 `reset()` 后可以从空流重放。

### 10.3 pyta2 子指标调用 hook

为了避免每个复杂 Signal 手写两套计算逻辑，core 提供一个受保护 helper：

```python
def _apply_pyta2(self, indicator, *args, **kwargs):
    if self._lifecycle_mode is UPDATE_LAST:
        return indicator.update_last(*args, **kwargs)
    return indicator.rolling(*args, **kwargs)
```

约束：

- 具体 Signal 的 `forward()` 始终写一份公式。
- helper 只在 `step()` / `update_last()` 调用链内使用。
- 不把 lifecycle mode 暴露为普通用户参数。
- 子指标对象不进入父 Signal 的深拷贝兜底；子指标由自身 `update_last()` 恢复状态。
- Signal 自己的中间 buffer 仍由 Signal 检查点协议管理。

### 10.4 required_window

组合 Signal 的窗口必须以原始 family 观测为单位，而不是简单取最大子指标窗口。

例如：

```text
SMA(inner_n) 的 SMA(outer_n)
required_window = inner_n + outer_n - 1
```

其它组合需要根据依赖链推导：

- 并行子指标后做同周期运算：通常取 `max(child.required_window)`。
- 串行 rolling：通常累加并减去重叠的当前点。
- 自定义延迟、差分或 horizon：必须显式写入公式和测试。

core 不尝试通过反射自动推导所有组合窗口。具体 Signal 对自己的 warmup 正确性负责。

### 10.5 schema 与 full_name

规则：

- 直接 bridge：复用 pyta2 schema/full name。
- 新的组合 Signal：定义自己的 schema/full name。
- 不允许组合 Signal 直接冒充某个子指标名称。
- full name 必须稳定、确定、包含影响数值语义的参数。
- field/binding、窗口、模式等影响结果的参数必须进入 full name 或 metadata。
- 显示名称不得包含对象地址、lambda repr 或不稳定字典顺序。

### 10.6 orderbook 完整示例：平滑深度失衡

推荐文件：

```text
sigma2/orderbook/smoothed_depth_imbalance.py
```

该信号先从完整盘口快照中计算前 `levels` 档深度失衡，再用 pyta2 `rSMA` 对最近 `n` 个快照进行平滑：

```python
from pyta2 import rSMA
from pyta2.utils.deque import NumpyDeque
from pyta2.utils.space import Scalar

from sigma2.core import rOrderBookSignal


class rSmoothedDepthImbalance(rOrderBookSignal):
    name = "smoothed_depth_imbalance"
    _update_state_fields = ("_imbalances",)

    def __init__(self, n: int, *, levels: int = 5, **kwargs):
        if n <= 0:
            raise ValueError("n must be greater than 0")
        if levels <= 0:
            raise ValueError("levels must be greater than 0")

        self.n = n
        self.levels = levels
        self._imbalances = NumpyDeque(maxlen=n)
        self._sma = rSMA(n, buffer_size=0)

        super().__init__(
            window=n,
            schema={
                "smoothed_depth_imbalance": Scalar(low=-1.0, high=1.0),
            },
            **kwargs,
        )

    def reset_extras(self):
        self._imbalances.clear()
        self._sma.reset()

    def forward(self, bids, asks):
        bid_depth = sum(float(size) for _, size in bids[: self.levels])
        ask_depth = sum(float(size) for _, size in asks[: self.levels])
        total_depth = bid_depth + ask_depth

        imbalance = (
            float("nan")
            if total_depth <= 0.0
            else (bid_depth - ask_depth) / total_depth
        )
        self._imbalances.append(imbalance)
        return self._apply_pyta2(self._sma, self._imbalances.values)

    @property
    def full_name(self):
        return f"smoothed_depth_imbalance(levels={self.levels},n={self.n})"
```

输入与状态语义：

- `step(bids=..., asks=...)` 的一条输入是完整 snapshot，不是 orderbook delta。
- bids/asks 已由 adapter 按价格排序并规范为 `(price, size)`；不足 `levels` 档时使用现有档位。
- Signal 只保存派生后的 `_imbalances`，不复制历史盘口，空间复杂度为 `O(n)`。
- `required_window = n`，表示至少需要 `n` 个盘口快照才能得到第一个有效 SMA。
- `step()` 通过 `_apply_pyta2()` 调用 `_sma.rolling()`。
- `update_last()` 恢复当前快照前的 `_imbalances`，用修订快照重新计算失衡，再调用 `_sma.update_last()`；两个 `g_index` 都不增加。
- schema 和 full name 属于新的 orderbook Signal；子指标 `SMA(n)` 仅记录在 component metadata 中。

这正是不能用通用 bridge 的例子：`bids/asks -> depth imbalance` 是有明确盘口语义的结构化派生，不应藏进匿名 extractor。

trade family 同理：先从 `price`、`volume`、`side` 形成 signed volume、arrival interval 或 impact，再把对应标量历史交给 rolling 指标。

## 11. Signal 自身状态检查点

### 11.1 为什么需要

`update_last()` 不能只替换输出。递推状态必须回到“当前观测进入前”再计算。

例如：

- EMA 不能对同一 bar 连续递推。
- 成交累计量不能先加旧成交再加新成交。
- orderbook pressure 的平滑状态必须撤销旧快照影响。

### 11.2 检查点模型

```text
step(new):
    保存观测前状态
    追加 family 输入
    执行 forward
    追加输出

update_last(revised):
    恢复观测前状态
    替换最后 family 输入
    执行同一 forward
    覆盖最后输出
```

Signal 内置实现应采用与 pyta2 相同的性能方向：

- 内置信号通过 `_update_state_fields: tuple[str, ...] | None` 显式声明紧凑状态字段。
- 标量直接保存。
- NumpyDeque 等容器使用轻量检查点。
- pyta2 子指标通过其公共 `update_last()` 自行恢复。
- 未审计的第三方 Signal 可以使用定向 deepcopy 兼容兜底。
- 顶层输出历史、schema 和不可变配置不进入热路径深拷贝。

`_update_state_fields` 语义与 pyta2 对齐：

- `()` 表示除 base/family 和嵌套组件外没有额外可变状态。
- `("field_a", "field_b")` 只检查点列出的私有状态。
- `None` 是旧类或第三方类的定向 deepcopy 兼容兜底，不是内置信号的推荐值。
- `rIndicator` / `rSignal` 子组件不被深拷贝，由它们自己的 `rolling/step` 与 `update_last` 生命周期恢复。

这是受保护的 Signal 作者接口；普通使用者只依赖 `step()` / `update_last()`。

### 11.3 嵌套 Signal

如果一个 Signal 内部调用另一个 Signal：

- append 模式下，子 Signal 使用 `step()`。
- revise 模式下，子 Signal 使用 `update_last()`。
- core 可以使用调用上下文自动传播 revise 模式。
- 父 Signal 不复制子 Signal 的完整输出历史。

组合优先使用 pyta2 子指标；只有子对象本身具有独立 family 语义时才嵌套完整 Signal。

### 11.4 异常语义

第一版采用 fail-stop，而不是假装所有第三方状态都能事务回滚：

- 可在生命周期开始前发现的输入、bind 和 arity 错误直接抛出，实例保持可用。
- `forward()`、子指标或输出 schema 校验在状态计算期间抛错时，原异常传播，同时实例标记为 faulted。
- faulted 后禁止继续 `step()` 或 `update_last()`，避免在未知私有状态上静默产生结果。
- 顶层 `g_index` 与输出缓存保留在最近一次成功提交的位置，但内部计算状态不承诺可继续使用。
- `reset()` 清除 faulted 和所有状态；runner 随后从已提交数据重放。

不为了罕见异常在每个事件上复制完整对象，也不承诺用一次 `update_last()` 修复失败的 `step()`。

## 12. 源码组织

### 12.1 推荐结构

初期保持扁平 family 目录：

```text
sigma2/
  core/
    signal.py
    kline.py
    orderbook.py
    trade.py
    pyta2.py              # 唯一 bridge 与生命周期 helper
  kline/
    return_.py
    gap.py
    sma.py
    mean_of_mean.py
    atr_breakout.py
  orderbook/
    book_spread.py
    depth_imbalance.py
    smoothed_depth_imbalance.py
  trade/
    trade_signed_volume.py
    rolling_trade_imbalance.py
  utils/
    ...
```

当单个 family 的信号明显增多后，允许 family 内增加第二层语义分类：

```text
sigma2/kline/trend/...
sigma2/kline/volatility/...
sigma2/orderbook/liquidity/...
sigma2/trade/flow/...
```

第一层始终是输入 family，不能改成 pyta2 风格的全局 `trend/`、`momentum/`，否则 orderbook/trade 的输入语义会丢失。

### 12.2 一信号一文件

稳定规则：

- 一个文件原则上只定义一个公开 Signal 类。
- 文件名使用信号语义的 snake_case。
- 私有小 helper 可以和 Signal 同文件。
- 跨多个 Signal 复用的 helper 才进入 `core/` 或 `utils/`。
- `__init__.py` 只做导出，不写实现。
- 顶层 `sigma2` 只 re-export 高频、稳定信号。
- 实验性信号只从 family 子包导出。

示例：

```text
mean_of_mean.py             -> rMeanOfMean
depth_imbalance.py          -> rDepthImbalance
rolling_trade_imbalance.py  -> rRollingTradeImbalance
```

### 12.3 不再建设 pyta2 镜像目录

长期目标不需要：

```text
sigma2/kline/pyta2/sma.py
sigma2/kline/pyta2/ema.py
sigma2/kline/pyta2/macd.py
...
```

这些一对一包装应由单一 bridge 取代。

如果 `sigma2.kline.sma.rSMA` 作为常用 family Signal 保留，它应是一个正常的 sigma2 Signal：

- 类名不暴露 pyta2 来源。
- 文件位于 `sigma2/kline/sma.py`。
- 内部可以复用 pyta2 `rSMA`。
- 它提供 K 线 field binding 和 sigma2 生命周期。
- 它不是机械生成的 adapter catalogue 成员。

## 13. 用户与二次开发接口

### 13.1 普通用户

普通用户只需要具体 Signal：

```python
from sigma2.kline import rMeanOfMean

signal = rMeanOfMean(5, 20, field="close", return_dict=True)

row = signal.step(
    open=100.0,
    high=103.0,
    low=99.0,
    close=102.0,
    volume=1200.0,
)
```

实时修订：

```python
row = signal.update_last(
    open=100.0,
    high=104.0,
    low=99.0,
    close=103.0,
    volume=1500.0,
)
```

普通用户不需要理解：

- pyta2 子指标如何检查点。
- Signal 私有 state fields。
- DequeTable 行更新。
- ContextVar。
- FeatureGraph。

### 13.2 Signal 作者

Signal 作者需要：

1. 选择正确 family 基类。
2. 定义构造参数和 schema。
3. 实现一份 `forward()` 公式。
4. 用 `_apply_pyta2()` 调用 pyta2 子指标。
5. 声明 Signal 自己额外维护的状态。
6. 正确计算 required window。
7. 定义稳定 full name。
8. 添加 replay 与 `update_last()` 一致性测试。

Signal 作者不需要：

- 自己写 output append/replace。
- 自己修改 `g_index`。
- 复制 pyta2 schema/full name。
- 为 append/`update_last()` 写两份数学公式。

### 13.3 runner 作者

最小 finalized-data 协议保持：

```python
class SignalLike(Protocol):
    family: str
    step_input_keys: tuple[str, ...]
    output_keys: list[str]
    schema: object

    def reset(self) -> None: ...
    def step(self, **data): ...
```

实时修订作为扩展协议：

```python
class RevisableSignalLike(SignalLike, Protocol):
    def update_last(self, **data): ...
```

这样 finalized batch runner 不被迫理解未完成 bar；在线 runner 可以显式要求 `RevisableSignalLike`。

## 14. 输出与身份契约

### 14.1 schema

- sigma2 继续复用 pyta2 的 `Schema` / `Space` 类型。
- 不创建 sigma2 自有的重复 schema 系统。
- 直接 bridge 使用子指标 schema。
- 组合 Signal 为新的业务输出定义 schema。
- `output_keys` 必须严格等于 schema keys。

### 14.2 full_name

- full name 是确定性的算法/信号描述，不要求单独承担全局列唯一性。
- 直接 bridge 的算法 full name 来自 pyta2。
- 组合 Signal 的 full name 由 Signal 自己定义。
- family、bind 和 output key 共同形成 runner 层唯一 identity。

### 14.3 meta_info

推荐稳定字段：

```text
name
full_name
family
step_input_keys
schema
output_keys
window
extra_window
required_window
g_index
```

推荐扩展字段：

```text
bind
components
signal_version
```

`components` 可以记录子 pyta2 指标的 meta_info，但不得包含可变运行状态或完整输出历史。

## 15. batch、研究与在线边界

### 15.1 batch

第一版 batch 使用逐条 replay：

```text
reset -> for row: step -> collect output
```

正确性规则：

```text
batch(finalized_data) == replay(step, finalized_data)
```

后续专用向量化实现必须通过该等价性测试。

### 15.2 在线

在线 adapter 根据数据源的 bar/event identity 决定：

```text
新观测       -> step()
最后观测修订 -> update_last()
```

Signal 本身不接收 `bar_id`，也不猜测时间边界。

### 15.3 research

研究训练层消费 concrete Signal，而不是 pyta2 primitive 或 bridge 私有对象。

```text
market data
  -> family Signal
  -> FeatureData
  -> TargetData
  -> ResearchDataset / AnalysisReport / Env
```

pyta2 组件可以出现在 Signal metadata 中，但 research runner 不依赖其内部实现。

### 15.4 Signal 与 effect / target

Signal 只能使用当前时刻已经可用的数据，输出 feature。依赖未来路径的收益、边界触发结果和标签不属于普通 `rSignal` 生命周期。

v5 边界：

- 正向 feature 使用 `rSignal.step()` / `update_last()`。
- 未来 outcome 使用独立 `rEffect`、target builder 或反向 batch 生命周期。
- `rEffect` 不因为 `rSignal` 新增 `update_last()` 就自动获得同名语义。
- 当前 `sigma2.kline.effect` 中以延迟输出包装 future effect 的类属于 v0.1 兼容实现，后续应单独评审迁移，不能反过来定义 Signal core。
- research 层必须保存 feature available time 与 target horizon，避免未来数据泄漏。

## 16. 错误语义

必须程序化区分或至少稳定区分以下错误：

| 场景 | 行为 |
| --- | --- |
| 首次 step 前 `update_last()` | `IndexError` |
| reset 后 `update_last()` | `IndexError` |
| family 输入缺字段 | `TypeError` 或明确输入错误 |
| bridge bind 缺少 pyta2 输入 | `ValueError` |
| bind 指向未知 family 字段 | `ValueError` |
| schema key 不匹配 | `ValueError` |
| 多输出 arity 不匹配 | `ValueError` |
| 子指标计算异常 | 原样传播或带上下文包装，不能吞掉 |
| 上次状态计算已失败 | 后续 step/update-last 抛 `RuntimeError`，直到 reset |
| 历史非最后位置修订 | core 不支持，由 runner reset/replay |

错误信息必须包含 Signal full name，并提示调用方可以采取的操作，例如先 `step()`、修正 bind 或 reset/replay。

## 17. 性能与资源边界

### 17.1 正常 step

- 内置信号不允许每个 step 深拷贝完整对象。
- 纯窗口 Signal 的检查点应为 O(1) 或只操作最后一行。
- 标量递推状态检查点应为 O(1)。
- pyta2 子指标使用其自身轻量检查点。
- 顶层输出历史不能进入状态快照。

### 17.2 update_last

- 目标复杂度应接近一次普通 step。
- 不允许默认重放全部历史。
- 不允许复制无限输出缓存。
- bounded family window 只替换最后一行。

### 17.3 缓存所有权

- pyta2 子指标输出缓存默认关闭，除非 Signal 公式确实读取它。
- Signal `outputs` 是短期运行缓存，不是完整训练矩阵。
- 长历史收集属于 runner / FeatureData。
- 一个状态容器只能有清晰的所有者。

## 18. 兼容与迁移

当前代码处于 `0.1.x`，v5 允许在 `0.2.0` 做有迁移说明的 core 扩展。

### 18.1 保留

- `rSignal`
- `rKlineSignal`
- `rKlineWindowSignal`
- `rOrderBookSignal`
- `rTradeSignal`
- `step()`
- `forward()`
- schema/output/full name 基本契约
- family 根目录结构
- 一个具体信号一个文件

### 18.2 新增

- `rSignal.update_last()`
- family 同签名 `update_last()`
- Signal 状态检查点协议
- pyta2 生命周期调用 helper
- 单一 pyta2 bridge

### 18.3 收敛

- `rPyta2Signal` 收敛为唯一兼容 bridge，而不是 pyta2 wrapper 基类族。
- `pyta2_signal(indicator_instance, family=..., bind=...)` 成为主接口，直接依赖传入实例的元信息。
- 当前 `pyta2_signal(str_or_type, params=..., field/inputs=...)` 保留一个 minor 的 deprecated 重载；字符串解析只委托 pyta2 registry，旧参数最终转换为同一个实例 bridge。
- `sigma2.utils.pyta2` 不再维护可扩张的重复指标 registry。
- `rPyta2SMA` 保留一个 minor 兼容周期，文档停止推荐。
- `sigma2/kline/pyta2/` 不再扩展新文件。
- 新 bridge 的 `full_name` 与 pyta2 实例严格相同，binding 移到 `meta_info["bind"]`；依赖旧 `SMA(...)[close]` 字符串列名的调用方需迁移到 runner identity。

### 18.4 不兼容变化纪律

- 已公开接口先标记 deprecated，再在后续 minor 移除。
- 兼容别名至少保留一个 minor。
- 同名 Signal 的数值语义发生变化时，必须提升 `signal_version` 或改变 full name。
- bridge 重构不能改变 pyta2 指标本身的 schema 和 output keys。
- 兼容适配器如需暂时暴露旧名称，只能使用单独的 `legacy_full_name` metadata，不能污染新 bridge 的算法 `full_name`。

## 19. Contract Tests

### 19.1 rSignal

- `step()` 只推进一次 `g_index`。
- `update_last()` 不推进 `g_index`。
- `update_last()` 不增加输出行。
- 重复相同 `update_last()` 结果幂等。
- `update_last()` 后继续 step 与最终序列重放一致。
- reset 清空 update-last checkpoint。
- return_dict、单输出、多输出行为一致。
- 计算失败不提前覆盖顶层输出。
- 状态计算失败后进入 faulted，reset 后可重新重放。

### 19.2 family

- `step()` 和 `update_last()` 使用相同关键字签名。
- K 线窗口 `update_last()` 只替换最后 OHLCV 行。
- orderbook snapshot 与 delta family 不混淆。
- trade 修订只表达最后事件替换。
- family 基类不默认保存不需要的历史。

### 19.3 pyta2 bridge

- schema 与 pyta2 实例相同。
- output keys 与 pyta2 实例相同。
- algorithm full name 与 pyta2 实例相同。
- window 元信息与 pyta2 实例相同。
- bind 完整性校验稳定。
- 已推进的 pyta2 实例、`rEffect`、无界窗口和结构化字段绑定会被拒绝。
- bridge 接管后关闭子指标输出缓存。
- 绑定标量逐条进入有界历史，传给 pyta2 的是正确顺序的数组。
- 连续 `update_last()` 只替换历史末项，Signal 与 pyta2 的 `g_index` 均不增加。
- step 映射到 `rolling()`。
- `Signal.update_last()` 映射到 `indicator.update_last()`。
- bridge 不依赖 pyta2 私有状态字段。
- bridge 不维护重复 registry。

### 19.4 组合 Signal

- 均值的均值与独立 NumPy/批量参考实现一致。
- 平滑深度失衡与“逐快照 depth imbalance 后再 rolling mean”的参考实现一致。
- orderbook 当前快照修订后继续 step，与只重放最终 snapshots 的结果一致。
- required window 等于真实首次有效位置。
- 子指标 `update_last()` 与最终序列重放一致。
- 多个 pyta2 子指标组合时不重复消费当前观测。
- component metadata 可追溯。

### 19.5 源码结构

- 每个公开 Signal 有独立实现文件。
- family 导入路径可用。
- 高频稳定 Signal 才从顶层导出。
- 不新增 `rPyta2Xxx` 镜像 catalogue。

## 21. 三轮查漏补缺

### 第一轮：是否仍然把 sigma2 做成 pyta2 桥接器

发现风险：如果继续增加 `rPyta2SMA`、`rPyta2EMA` 等类，源码数量增长但没有新增信号语义。

修正：

- 只保留一个通用 bridge。
- 不复制 pyta2 registry、schema 和 full name。
- 具体 sigma2 信号必须有 family 语义或组合逻辑。

结论：边界清晰。

### 第二轮：复杂组合是否能正确支持 update_last

发现风险：组合 Signal 的 `forward()` 若总是调用子指标 `rolling()`，修订当前 bar 时会重复消费状态。

修正：

- core 提供 `_apply_pyta2()` 生命周期 helper。
- step 时调用子指标 `rolling()`。
- update-last 时调用子指标 `update_last()`。
- Signal 自己的中间 buffer 使用检查点恢复。
- bridge 维护标量绑定字段的历史数组，不能把单个 close 直接传给 pyta2。
- reset 显式清理子指标与中间 buffer。
- 状态计算异常采用 fail-stop，避免在部分恢复状态上继续推进。
- 增加最终序列 replay 等价性测试。

结论：一份公式可以安全支持 append 与 revise。

### 第三轮：family 是否被 K 线模型污染

发现风险：pyta2 主要以价格数组为输入，容易让 orderbook/trade 被压成通用 values 而失去市场结构。

修正：

- 第一层始终按 family 组织。
- family 公共接口每次接收一条观测，并使用显式 keyword-only 签名。
- pyta2 只计算 family 信号内部的局部数值序列。
- orderbook/trade 的派生、事件顺序和结构逻辑留在具体 Signal。
- 通用 bridge 只绑定直接标量字段，不接受把结构化数据隐藏在 extractor 中。
- snapshot 与 delta 使用不同 family。

结论：pyta2 是计算积木，不是 sigma2 的数据模型。

## 22. 最终判断

v5 的稳定关系是：

```text
market event
  -> Signal family
  -> concrete sigma2 Signal
       ├─ pyta2 indicator(s)
       ├─ family-specific logic
       └─ custom state
  -> Signal output
  -> runner / research / online application
```

直接桥接只是旁路：

```text
single pyta2 indicator
  -> one thin bridge
  -> Signal lifecycle
```

不再采用：

```text
pyta2 catalogue
  -> one sigma2 wrapper class per indicator
  -> sigma2 mirror catalogue
```

sigma2 的长期核心应是：

```text
独立、可组合、具有明确市场数据语义的 Signal 类库。
```
