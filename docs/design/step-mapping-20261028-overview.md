# 字典协议作为算子输入的设计草案

创建时间：2026-10-28 14:33 CST
状态：sigma2 字典接口已实施；实施步骤与验证见 `docs/dev/PLAN-030-kline-mapping.md` 及对应结果。

> Bundle 字典从 0.9.0 起以[截面字典结构](bundle-snapshot-20261028-overview.md)为准，默认字段为 `bundle` 和可选的 `open_time`。本文第 3 节和第 4 节有关 Bundle 的结构和旧对象描述保留为 0.8.0 的设计记录。

## 1. 背景和目标

本次按用户反馈调整：`step()` 接收一个字典，满足必需字段即可，允许额外字段。单 symbol 与多 symbol 输入都采用字典协议，不要求调用者构造特定类。`step()` 仍表示推进一个逻辑时点；schema 和 `result_index` 沿用现有设计，时间可选时的批量结果索引需要重新确定。

已确认的单 K 线规则：`open`、`high`、`low`、`close` 四个逻辑字段必须存在；`volume`、`symbol` 和时间可选。具体 Signal / Outcome 如依赖 `volume` 或其他字段，再要求其存在。允许指定输入字段的 key 映射。单次 `step(bar)` 不展开字典。

## 2. 单 symbol 输入

示例：

```python
bar = {
    "open": 100.0, "high": 102.0, "low": 99.0, "close": 101.0,
    "symbol": "BTCUSDT", "open_time": 1735689600000,
    "other_field": 42,
}
signal = rKlineMA(20)
value = signal.step(bar)
```

- 输入使用只读映射协议，普通 `dict` 可以直接传入；额外字段不导致拒绝，供需要它们的算子读取。
- 单 K 线基础协议要求四个 OHLC 逻辑字段，可以通过字段映射从其他名字的输入键读取。算子声明自身额外必需字段；例如 `rKlineMA(field="volume")` 要求 `volume`，默认 close 均线不要求它。
- 缺少必需键在推进状态之前报错；数值缺失和非法值的处理按各算法的定义执行。
- 标的和时间可选；无时间时，`g_index` 表示调用方传入的顺序，无法由输入推断实际可用时间。
- 对已声明必需字段保存输入快照，避免调用者复用并修改行情字典后改变已经处理的数据。不复制不使用的额外字段；自定义算子如需持有无法复制的可变对象，应自行管理其状态快照。

### 字段映射

映射用于适配数据来源的字段名，不改变一次 `step()` 接收一个字典的形式。本次采用“算子使用的逻辑字段 → 输入字典的实际字段”，使用 `key_map` 参数：

```python
bar = {
    "open": 100, "high": 102, "low": 99,
    "close": 101, "open_time": 1735689600000,
    "extra": 42,
}
signal = rKlineMA(20, key_map={"date": "open_time"})
value = signal.step(bar)
```

示例中的 `close` 使用标准行情字段；如果某个自定义算子需要 `date`，它读取 `bar["open_time"]`。当前内置均线不需要 `date`，映射本身不会使 `date` 变为必需字段。`date` 不是 sigma2 已定义的通用时间字段；该映射不会自动设置 `bar_time` 或 `available_at`。如需将数据源的 `open_time` 作为批量输出的行情时间，可明确指定 `{"bar_time": "open_time"}`。

指定映射的位置可以有两种：

| 方案 | 使用方式 | 优点 | 代价 |
| --- | --- | --- | --- |
| A：配置算子 | 创建算子时指定 `key_map`，批量接口传入同一配置 | 每次 `step()` 直接传原字典，适配规则属于该算子的输入契约 | 多个算子共享数据源时需复用配置；组合算子须避免重复映射 |
| B：独立输入适配器 | 上游按配置转换或包装字典，再传给算子 | 同一份数据可供多个算子复用，算子本身保持简单 | 调用方和批量接口要统一使用适配器，需明确额外字段及冲突处理 |

建议以 A 为公开使用方式，内部可复用 B 的映射逻辑。映射按以下规则设计：

- 未指定的逻辑字段沿用同名输入键；映射作用于 OHLC、算子要求的其他字段，以及需要读取的可选字段。映射后的 OHLC 满足基础必需字段要求。
- 指定映射时，以显式指定的实际键为准；即使字典中也有同名逻辑键，也不静默改用它。映射的必需字段缺失时，应在推进状态前报错；映射的可选字段缺失时仍可省略。
- 各映射直接从原始输入读取，不依靠重命名顺序，也不做链式映射。这样交换两个字段名时不会互相覆盖。
- 映射只解析字段名，不更改输入字典、推断数据类型或时间含义；其他输入键仍可供自定义算子使用。如果映射覆盖同名逻辑键，逻辑视图读取映射后的值，原字典仍保留原值。
- `field="close"` 选择算法使用的逻辑字段；`key_map` 决定从输入的哪个键取值，两者职责不同。自定义算子也需要通过同一逻辑视图读取字段，避免绕过映射。
- 映射配置在算子生命周期内保持一致。逐步执行、窗口保存、批量重放以及截面映射到子算子时，需使用相同的解析规则，且只在适当边界转换一次。
- 记录映射配置供追溯。不同映射可能让相同公式读取不同数据；若其结果同时保存，应通过结果名称或存储标识区分，防止 `factor_names` 冲突。公式名称保持逻辑字段语义，元信息中记录实际映射；汇总同名不同来源的结果时由调用方检测冲突、指定别名或使用不同的数据集标识。

### 可选元信息如何处理

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 上游维护时间和标的顺序 | 基础算子按输入顺序推进；可选元信息不强制参与校验 | 输入要求最少，但顺序和身份由上游保证 |
| 提供元信息时自动校验 | 识别约定字段后校验标的和时间递增 | 能发现部分错误；必须先统一字段名、时间单位和混合缺失的规则 |

字典采用第一种；当算子显式配置 `symbol` 且字典中也提供 `symbol` 时，两者需要一致。旧对象输入继续保留其已有的身份和时间校验。批量元信息按 `bar_time` / `available_at` 字段获取，缺失则保持未知，不从 `open_time` 猜测可用时间。

## 3. 多 symbol 截面输入

一个 Bundle 仍表示同一逻辑时点的截面。固定 symbol 顺序由算子配置决定；缺失标的不在当次行情中，其位置输出缺失值，不使用其他时点的数据补齐。每个存在的标的按第 2 节校验行情字段。

可选字典结构：

| 方案 | 示意 | 优点 | 代价 |
| --- | --- | --- | --- |
| A：使用 `bars` 字段 | `{"bars": {"BTC": bar, "ETH": bar}, ...}` | 截面行情和时间等额外信息有明确位置 | 多一层 `bars` |
| B：直接按 symbol 映射 | `{"BTC": bar, "ETH": bar}` | 输入短，贴近截面 | 无法直接区分顶层额外字段与 symbol；时间需要另行表达 |

采用 A，例如：

```python
bundle = {
    "bars": {
        "BTCUSDT": {"open": 100, "high": 102, "low": 99, "close": 101},
        "ETHUSDT": {"open": 200, "high": 202, "low": 198, "close": 201},
    },
    "open_time": 1735689600000,  # 可选的附加信息
}
rank = rKlineBundleRank(
    symbols=("BTCUSDT", "ETHUSDT"),
    bundle_key_map={"bar_time": "open_time"},
)
values = rank.step(bundle)
```

- `bars` 为该时点的 symbol 到 K 线字典映射；额外的顶层字段允许保留。
- 算子持有固定 `symbols`，其顺序也是结果数组的顺序。在线调用不要求每个快照重复携带完整全集。
- 批量处理应由调用者显式提供完整 `symbols`，或在第一份快照中显式提供完整全集；不从第一份可能不完整的 `bars` 猜测全集。全集之外的 symbol 报错。
- 已出现的 Bar 缺少算子必需字段时，在推进截面及子算子状态前报错；整个 Bar 不存在则按缺失标的处理。例如按 `volume` 排名时，存在的 Bar 需提供 `volume`。
- 同一快照内各 symbol 的同步及缺失判定由上游负责；不含时间的字典不能提供真实可用时间。
- 自定义 Bundle 算子的 `required_fields` 声明每个存在的 Bar 的附加字段，`required_bundle_fields` 声明截面顶层的附加字段，均在推进前检查。

字段映射也适用于 Bundle：`key_map` 一致地应用到 `bars` 中每个存在的 Bar，symbol 名称不参与字段映射。Bundle 自身的 `bars` 和顶层时间键使用独立的 `bundle_key_map`，避免与每个 Bar 的字段混淆。批量和单步使用相同规则。

## 4. 兼容与消费端适配

现有对象输入有两种处理方式：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 字典为唯一公开输入 | 接口简单，使用者无需依赖数据类 | 现有 `KlineBar` / `KlineBundle` 调用需要迁移 |
| 字典为主要协议，同时保留对象适配 | 现有调用者可以逐步迁移 | 需要维护对象与字典的一致语义 |

本次以字典协议为主要契约，同时保留现有对象输入。字典调用者无需构造对象。

适配 `crypto.factor_make` 时，建议：

1. 在 `factor_make/engine.py` 中将 `signal.step(**bar)` 改为 `signal.step(bar)`，直接使用已有行情字典。
2. 对照旧 `required_window` 的读取边界和新属性：Signal 的 `min_periods = n_backward + 1`；先用逐信号核对后的 `min_periods` 保持旧读取长度，避免把 `n_backward` 直接当成旧窗口长度而少读一根。
3. 将未来方向样板迁为 `rKlineWindowOutcome`，按 `result_index` 或 `forward_outcome_apply()` 对齐所属锚点；同步修订依赖旧确认时点输出排列的行整理逻辑，保留实际确认 Bar 的时间。保留原来的阈值与端点有效性规则；当前 sigma2 内置未来收益要求整个未来区间有效，不能直接替换而改变结果。
4. 核对项目其他自定义 Signal 和 CLI 对旧 `window` / `required_window` 的引用。`rMACross` 还依赖尚使用旧时间接口的 pyta2 实现，需单独确认处理方案，不能仅修改调用签名就视为全部兼容。

K 线窗口仍向窗口算子提供 OHLCV 数组；可选 `volume` 缺失时使用缺失值。批量接口从逻辑字段读取可选的 `bar_time` 和 `available_at`：无时间或部分时间缺失时表格按输入位置索引，元信息保留输入时间；不伪造时间或推断实际可用时间。

该消费项目已有未提交改动，包括 `engine.py`；后续实施时须在现有内容上局部修改并保留这些改动。sigma2 的 README 和使用 skill 已同步字典输入协议。

## 5. 三轮检查

1. **输入与扩展**：单 K 线 OHLC 逻辑字段必需，volume 等额外字段由算子按需声明；映射不使可选字段变为必需字段，附加字段不会导致拒绝。
2. **截面与时间**：固定 symbol 顺序、缺失标的和共同时间轴要明确；Bar 字段与 Bundle 顶层字段的映射作用域不能混淆；可选时间不能被当作实际可用时间；第一份稀疏快照不能代表完整 symbol 集合。
3. **迁移与状态**：输入字典被复用时，窗口内状态不应随之改变；缺少必需字段不得先推进索引；逐步、批量及组合算子的映射要一致；未来结果的批量回填和旧消费端的行排列需一起迁移。

## 6. 本次实施取舍

采用 Bundle 结构 A、保留对象兼容、使用算子配置中的逻辑字段到输入字段映射；Bundle 顶层映射与 Bar 映射分开。未知 symbol 报错。相同公式应用于不同数据来源时，`factor_names` 不自动改写；消费端须结合映射元信息或数据集标识区分，避免覆盖。消费项目的迁移在 sigma2 接口完成后进行。
