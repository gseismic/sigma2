## 结论

sigma2 已能管理 `step()`、`update_last()` 和 pyta2 子指标的修订分派；当前发现的主要问题是**自定义组合 Signal 缺少无下划线的公开扩展入口**。外部子类若在一个 Signal 中组合多个有状态 pyta2 指标，现有推荐方式要求调用基类受保护的 `_apply_pyta2()`。它只选择 pyta2 的 `rolling()` 或 `update_last()`，不实现指标计算。这个方法是设计稿有意提供的作者 hook，并非误用偶然存在的私有实现；但下游若要求稳定、清晰的公开样板，仍要依赖受保护命名。`rPyta2Signal` 适配单个指标，不能直接表达多指标与自定义逻辑的组合。组合 Signal 的自有中间状态还需通过受保护字段 `_update_state_fields` 声明，这是样板能否完全避开受保护命名的关联问题，需在后续设计中单独决定。

本次未发现现有内置信号的数值错误。`python -m pytest -q` 在上述版本运行结果为 **81 passed**。

## 前因后果：为什么会遇到这个问题

下游项目需要从 1 分钟 K 线创建新的因子：Signal 应直接继承 sigma2 的 K 线基类，负责字段选择、窗口、输出名称及 `step()` / `update_last()`；pyta2 只是其中一种计算工具。自定义信号可能调用零个、一个或多个 pyta2 指标，也可能混入自定义市场逻辑。不能要求每个新 Signal 先写成一个新的 pyta2 指标类，否则业务语义和计算工具的边界会倒置。

最简单的盘口价差 `rBookSpread` 只读取当前 bids/asks，公式写在 `forward()` 中即可；它不持有 pyta2 子指标，因而不需要桥接。若 Signal 组合有状态的 pyta2 `rSMA` 或 `rEMA`，`forward()` 会在新增观测和修订观测时都被调用，子指标却必须分别收到 `rolling()` 和 `update_last()`。sigma2 的 `_apply_pyta2()` 正是为此产生，并已在内置信号中使用。问题是在下游自定义 Signal 中，它成为实际必需的受保护接口。

下游 `SMA of SMA` 样板的迭代暴露了这一点，当前文件是 `../../projects/crypto.factor_make/factor_make/signals/trend/sma_of_sma.py`：先直接调用 `_apply_pyta2()`，因受保护命名不适合公开扩展样板而改为调用 pyta2 `forward()`、比较两边 `g_index`、逐根运行批量 `SMA`，最后尝试每根 `reset()` 后调用 `rSMA.rolling()`。这些改写有的绕开 pyta2 生命周期，有的推断 sigma2 内部状态，有的增加重复计算；最后一种只碰巧适用于完整窗口可计算的 SMA。需求并非让 sigma2 计算 SMA，而是让它以公开契约传递自己的新增或修订生命周期。

这项问题在创建**组合信号**时出现，普通用户直接调用已经存在的 `rKlineMA` 等信号不受影响。当前测试通过说明现有桥接行为可用；它不能消除下游扩展必须使用受保护方法这一接口问题。

## 哪些场景需要桥接

| 场景 | Signal 做什么 | pyta2 做什么 | 是否需要子指标生命周期桥接 |
| --- | --- | --- | --- |
| 当前盘口价差，见 `sigma2/orderbook/book_spread.py:25-30` | 取最优买卖价并相减 | 不参与 | 不需要；`forward()` 直接计算 |
| 单个现成 SMA/EMA 绑定到 K 线字段 | 绑定 `close` 等字段，提供 Signal 身份 | 一个指标持续计算 | 调用方直接用 `rKlineMA` 或 `rPyta2Signal`，桥接已封装在内 |
| 先取 `HLC3` 再做 EMA | 自定义价格派生、名称和输出 | `rEMA` 维护递推状态 | 需要；派生逻辑使单指标适配器不足以直接表达完整 Signal |
| 连续两级 SMA 或 EMA | 选择字段、缓存第一级输出、定义组合窗口和输出身份 | 两个指标各自持续计算 | 需要对两个子指标分别分派，并恢复 Signal 自有的中间缓存 |
| 盘口深度失衡后平滑，见 `tests/test_signal_update_last.py:103-160` | 提取多个档位的深度失衡 | `rSMA` 平滑历史失衡值 | 需要；同一问题存在于 orderbook family，不限 K 线 |
| 自定义纯函数或完整窗口公式 | 从当前观测或 sigma2 窗口直接算值 | 可调用无状态函数，也可完全不参与 | 不需要；没有独立子指标状态 |

由此可见，公开桥接不是每个 Signal 都必须使用的新抽象。它只服务于**Signal 持有 pyta2 `rIndicator` 子对象，并需要保持该对象的连续状态**这一类场景。

## 当前调用链与证据

1. `sigma2/core/signal.py:116-168`：`step()` 和 `update_last()` 分别设置私有 `_lifecycle_mode`，然后调用对应的 `_step_forward()` / `_update_last_forward()`。
2. `sigma2/core/kline.py:73-122`：窗口型信号在新增时追加 OHLCV、在修订时替换末行；两条路径最终都调用子类的同一个 `forward()`。外部子类从 `forward()` 的参数本身无法判断当前是新增还是修订。
3. `sigma2/core/signal.py:178-187`：`_apply_pyta2()` 根据私有模式分派到 pyta2 `rolling()` / `update_last()`。这个方法是生命周期桥接，不计算 SMA、EMA 等指标值。
4. `sigma2/core/pyta2.py:34-71`：公开的 `rPyta2Signal` 持有一个 `_indicator` 并调用受保护桥接方法，适合直接适配单个 pyta2 指标。
5. `docs/design/sigma2-20260922-v5.md:741-812` 和 `skills/sigma2-usage/references/add-signals.md:33-41`：组合 Signal 的设计和开发指南都要求扩展作者使用 `_apply_pyta2()`；`tests/test_signal_update_last.py:103-160` 的组合示例也采用该方法。

### 新增与修订在同一个 `forward()` 中的差别

| 调用方操作 | sigma2 对窗口和索引的动作 | 子 pyta2 指标必须做的动作 | Signal 自有缓存 |
| --- | --- | --- | --- |
| `step(new_bar)` | 追加观测，Signal `g_index` 加一 | 对当前输入调用一次 `rolling()`，建立子指标本根观测前的检查点 | 追加本根中间值 |
| `update_last(revised_bar)` | 恢复 Signal 自有状态、替换窗口末行，索引不变 | 对同一根的修订输入调用 `update_last()`，恢复子指标原检查点后覆盖结果 | 从观测前状态重新生成本根中间值 |
| 再次 `update_last()` | 再次从同一检查点重算 | 再次修订同一根，不累计消费 | 结果应幂等 |
| 下一次 `step()` | 在已修订的状态上追加新观测 | 从修订后的子指标状态继续 `rolling()` | 在修订后的缓存上继续追加 |
| `reset()` | 清空 Signal 窗口、索引和输出 | 子指标也必须 `reset()` | 自有缓存清空 |

以 `n=3` 的两级 SMA 为例：收盘价依次为 `[1, 2, 3, 4, 5]` 时，第一级最后三个有效输出为 `[2, 3, 4]`，第二级在第五根输出 `3`。若把第五根收盘价修订为 `8`，正确的第一级最后三个值是 `[2, 3, 5]`，第二级应为 `10/3`；Signal 和两个 pyta2 子指标的索引仍停留在第五根。只把窗口最后的值换掉不够：第一级子指标、第二级子指标和 Signal 自有缓存都必须按各自的修订规则恢复后重算。

## 问题及影响

### 1. 必需的扩展能力只有受保护入口

组合信号需要让每个 pyta2 子指标在新增观测时调用 `rolling()`，在修订最后观测时调用 `update_last()`。sigma2 已实现这段分派，却只通过 `_apply_pyta2()` 提供。设计稿明确称它为“受保护生命周期桥接 hook”；因此当前代码有一条可用的子类扩展路径，问题是没有无下划线的公开路径。按照文档编写的外部信号必须调用受保护方法；若坚持只使用公开接口，就需要自己重复实现分派。触发场景是两级 SMA、盘口失衡后平滑、ATR 标准化等多组件信号。依据：`sigma2/core/signal.py:178-187`、`docs/design/sigma2-20260922-v5.md:721-741,800-815`。

### 2. 公共单指标适配器不能填补组合入口

`rPyta2Signal` 的构造与 `forward()` 围绕一个 `_indicator`，没有多组件计算和中间状态的组合接口。要求调用方先把整套业务逻辑封装为新的 pyta2 `rIndicator`，会把本应属于 sigma2 Signal 的字段绑定和组合语义移入计算工具层。此处是适配器的预期边界，不是适配器实现错误。依据：`sigma2/core/pyta2.py:34-71`、`docs/design/sigma2-20260922-v5.md:721-739`。

### 3. 现有替代写法会转移生命周期负担

- 比较 Signal 与 pyta2 子指标的 `g_index` 来推断修订，依赖两个对象的推进顺序；这不是公开的模式契约。`sigma2/core/signal.py:121-155` 的调用顺序变化可能令该推断失效。
- 每次 `forward()` 都重置子指标再调用 `rolling()`，对只由当前完整窗口决定输出的 SMA 可得到正确值，却丢弃 pyta2 的持续状态；EMA 等递推指标不能如此使用。
- 每根观测用 pyta2 批量函数重算整个窗口可避免状态分派，但会重复计算；它不适合作为需要处理长 K 线序列的通用样板。

逐根重置为何不能成为通用样板，可以用递推 EMA 直接复现。对输入 `[1, 2, 3, 10, 4]` 和 `n=3`，持续对同一个 pyta2 `rEMA` 调用 `rolling()`，第三至第五根输出分别为 `2, 6, 5`；每根先 `reset()` 再对当前三根窗口调用 `rolling()`，输出变成 `2, 5, 5.666666666666667`。原因是 `pyta2/pyta2/trend/ma/ema.py:40-73` 的 EMA 有内部 `ema` 状态：重置后每根都按窗口 SMA 重新初始化，丢失先前的递推结果。该数值对照在上述 pyta2 提交上用公开 `reset()` / `rolling()` 接口直接运行得到。

另一个边界是 pyta2 `forward()`：它由 `rIndicator.rolling()` / `update_last()` 在内部调用，直接调用不会建立或恢复其检查点。把它当作使用者入口，即使当前 `rSMA` 恰好按传入窗口得到正确数值，也无法替代一般有状态指标的生命周期。

这些写法说明公开桥接入口的缺失对调用方有实际影响；不能把它们直接认定为 sigma2 当前数值错误。

`reset()` 有明确的合法场景：新建序列后重放、显式从空流重新开始，以及计算失败后按 sigma2 的 faulted 契约恢复。它会清掉 pyta2 的递推状态和最后一根的检查点，不应被当作每根观测的分派手段；如果样板依赖逐根重置才能避免调用 `_apply_pyta2()`，后续换成 EMA 时就会悄悄改变数学结果。依据：`sigma2/core/signal.py:189-202`、`pyta2/pyta2/base/indicator.py:122-165`。

### 4. 文档把受保护方法写成常规扩展步骤

总设计的两级均值和盘口示例、使用指南、组合测试一致地使用 `_apply_pyta2()`。这保证了既有行为，却同时向下游开发者传达“写自定义 Signal 必须调用下划线方法”。如果只改一个项目样板，不改 sigma2 的公开契约与指南，新扩展仍会反复面对相同选择。依据：`docs/design/sigma2-20260922-v5.md:783-815,900-925`、`skills/sigma2-usage/references/add-signals.md:33-41`。

### 5. 自有中间状态的声明仍是受保护扩展约定

两级均值需要保存第一级输出队列，盘口深度失衡后平滑需要保存失衡值队列。修订最后一根时，sigma2 必须先恢复这些 Signal 自有的可变状态，再让 pyta2 子指标调用 `update_last()`；否则即使子指标正确修订，传给它的中间序列也可能包含旧末值和新末值两份。当前可行做法是在子类声明 `_update_state_fields = ("_first_values",)` 等字段，core 在 `step()` 前检查点，在 `update_last()` 前恢复；生命周期子组件不能放入这个列表。依据：`sigma2/core/signal.py:45,121-155,205-245`、`tests/test_signal_update_last.py:103-160`。

这套状态恢复机制本身有用，设计稿也明确把 `_update_state_fields` 列为“受保护的 Signal 作者接口”（`docs/design/sigma2-20260922-v5.md:963-977`）。若目标是“自定义 Signal 样板只使用无下划线的公开扩展入口”，仅公开 `_apply_pyta2()` 仍会留下这一处。后续需要决定是继续承诺这个受保护作者契约并明确其稳定性，还是提供无下划线的字段声明或公开检查点 hook；不能把命名偏好误称为当前计算错误。这个决定和子指标分派是两个问题；不应为了去掉下划线而让框架自动深拷贝 pyta2 子指标。

## 为什么应在 sigma2 解决

- 新增或修订是 sigma2 Signal 的生命周期事实，只有 sigma2 在进入 `forward()` 前明确知道当前模式；让每个下游项目通过 `g_index`、重置子指标或重复批量计算来猜测，分散了同一规则。
- pyta2 对指标算法、递推状态、`rolling()` 和 `update_last()` 负责。sigma2 的桥接只选择调用哪个公开方法，计算边界不变。
- 下游应继续直接继承 `rKlineSignal`、`rKlineWindowSignal`、`rOrderBookSignal` 等 family 基类，在 Signal 中写市场语义。公开桥接能保留这条短路径，而不要求每个组合信号都新增 pyta2 类或通用编排框架。
- 若要把样板用于后续扩展，公开接口、测试和指南必须对齐；单独把 `_apply_pyta2()` 改成项目本地 helper 只会把依赖位置移动一层。

## 边界与可选修正方向

| 方向 | 收益 | 代价或限制 |
| --- | --- | --- |
| 保持 `_apply_pyta2()` 现状 | 无代码变更，现有内置信号正常 | 外部组合信号继续依赖受保护方法 |
| 提供公开的子指标生命周期调用方法，保留旧方法兼容 | 外部信号可直接继承 family 基类；pyta2 仍负责计算；无需推断模式 | 需要确定命名、仅在 `step()` / `update_last()` 内调用的契约、错误行为及文档迁移 |
| 暴露当前生命周期模式供调用方自行分派 | 基类改动小 | 每个组合信号重复分支逻辑，易遗漏修订或状态恢复 |
| 扩展 `rPyta2Signal` 为多组件通用编排器 | 可能隐藏全部分派 | 增加配置和状态模型，削弱直接继承 Signal 写业务逻辑的简单路径 |

若后续实施，优先评估**公开生命周期分派方法**：它只负责调用 pyta2 的公共 `rolling()` / `update_last()`，不承担指标算法；保留 `_apply_pyta2()` 兼容既有子类，并把组合指南改为公开调用。同时评估 `_update_state_fields` 的作者契约是否需要公开化。具体名称、生命周期外调用行为、状态所有权和兼容策略应在实施设计中定稿，本问题文档不预先宣称 API 已存在。

预计修改范围很小：`rSignal` 的桥接入口及契约、内置调用方和扩展指南、组合信号测试、下游样板。`rKlineWindowSignal` 仍负责原始 OHLCV 窗口；`_update_state_fields` 仍用于 Signal 自己的中间缓存，pyta2 子指标继续由自身 `update_last()` 恢复。公开桥接不会自动推导组合窗口，不替下游定义 schema 或 full name，也不替代无状态自定义公式。

## 后续验证要点

- 外部自定义 `rKlineWindowSignal` 能组合两个 pyta2 子指标，不调用受保护方法，也不比较 `g_index` 或每根重置指标。
- 中间缓存的修订与子指标修订分别由谁负责有清晰的公开说明；样板不依赖未承诺的内部字段名，或明确记录该字段已成为受支持的作者契约。
- 预热期间、连续 `update_last()`、修订后继续 `step()`、显式 `reset()` 与完整序列重放等价；至少用一个递推型子指标验证，避免仅靠 SMA 掩盖状态错误。
- 错误输入、生命周期外调用及子指标异常的行为明确；现有内置信号、`rPyta2Signal` 和旧受保护入口维持兼容。
- 文档示例、扩展指南、测试和实际公开接口一致。
