# pyta2 与 sigma 分层设计 v3

## 背景

v2 提出了 `IndicatorDef + FeatureSpec + FeatureEngine` 三层模型。重新阅读 `pyta2/base/indicator.py`、`pyta2/stats/atr/atr.py`、`pyta2/momentum/macd/macd.py` 后，需要修正一个关键判断：

`IndicatorDef` 不应该在 sigma 中完整定义。`pyta2` 的 rolling 指标对象已经包含了很多指标定义信息，包括输出 schema、输出键、真实窗口、完整名称和元信息。sigma 再维护一份完整 `IndicatorDef`，容易造成重复定义和不一致。

v3 的方向是：

1. `pyta2` 指标实例是指标元信息的事实来源。
2. sigma 只补充市场数据路径绑定、feature 命名、组合计算和执行编排。
3. sigma 支持外部行情源 feature，也支持基于已有 feature 再计算新 feature。

## 代码事实

### rIndicator 已经定义的能力

`rIndicator` 是 `pyta2` rolling 指标的基础抽象，已经提供：

- `window`
- `extra_window`
- `required_window = window + extra_window`
- `schema`
- `output_keys = list(schema.keys())`
- `return_dict`
- `outputs`
- `full_name`
- `meta_info`
- `rolling(*args, **kwargs)`
- `make_dict_output(output)`

其中输出键不是外部文档推断出来的，而是由子类传入的 `schema` 决定。

例如单输出指标：

```python
schema=[
    ("atr", Box(...)),
]
```

多输出指标：

```python
schema=[
    ("dif", Box(...)),
    ("dea", Box(...)),
    ("macd", Box(...)),
]
```

因此，sigma 不应该再写：

```python
output_fields=["atr"]
```

或者：

```python
outputs=("dif", "dea", "macd")
```

这些信息应该从实例读取：

```python
obj = rMACD(n1=26, n2=12, n3=9, return_dict=True)
obj.output_keys
obj.required_window
obj.meta_info
```

### rATR 的真实形态

`rATR` 的构造参数：

```python
rATR(n=20, ma_type="EMA", **kwargs)
```

`forward()` 签名：

```python
forward(highs, lows, closes)
```

输出 schema：

```python
("atr", ...)
```

它内部维护：

- `values_TR`
- `fn_ma`

这说明 ATR 是一个结构化 K 线指标，但其内部依然可以组合已有 MA 指标。

### rMACD 的真实形态

`rMACD` 的构造参数：

```python
rMACD(n1=26, n2=12, n3=9, **kwargs)
```

`forward()` 签名：

```python
forward(values)
```

输出 schema：

```python
("dif", ...)
("dea", ...)
("macd", ...)
```

真实窗口：

```python
window = n1 + n3 - 1
```

这说明不能简单假设所有指标都有一个 `window` 参数。低层 feature 声明应该使用 pyta2 的真实构造参数名，例如 `n`、`n1`、`n2`、`n3`。用户友好的 `window` 可以作为 sigma DSL 的别名，但不应成为底层规范。

## v3 核心判断

### 不再设计完整 IndicatorDef

v2 中的 `IndicatorDef` 试图描述：

- 后端名称
- 指标类
- 输入参数名
- 输出字段
- 窗口参数

v3 中只保留一个很薄的 pyta2 适配逻辑：

```python
obj = cls(**params, extra_window=extra_window, return_dict=True)

input_keys = inspect_forward_inputs(obj.forward)
output_keys = obj.output_keys
required_window = obj.required_window
schema = obj.schema
meta = obj.meta_info
```

也就是说：

- 输出字段来自 `obj.output_keys`
- 窗口来自 `obj.required_window`
- schema 来自 `obj.schema`
- 完整名称来自 `obj.full_name`
- 输入字段名来自 `forward()` 签名或显式绑定校验

sigma 不再重复维护一份完整指标定义 registry。

### sigma 需要保留的抽象

sigma 仍然需要自己的 feature 声明，因为 pyta2 不知道：

- `values` 应该绑定到 `kline.close` 还是 `kline.volume`
- `highs/lows/closes` 应该来自哪个行情源
- feature 输出列在 ML 矩阵中叫什么
- 多个 feature 如何共享 buffer
- 一个 feature 是否依赖另一个 feature 的输出
- batch 和 rolling 如何用同一份声明执行

因此，v3 的核心抽象是：

```python
FeatureSpec
FeatureGraph
FeatureEngine
Pyta2Adapter
```

## FeatureSpec

`FeatureSpec` 描述一次真实 feature 计算。

```python
@dataclass(frozen=True)
class FeatureSpec:
    name: str
    cls: type[rIndicator]
    params: dict[str, object]
    bind: dict[str, str]
    namespace: str = "feature"
    extra_window: int = 0
    outputs: str | dict[str, str] | None = None
```

字段含义：

- `name`：feature 节点名，也是单输出 feature 的默认列名。
- `cls`：pyta2 rolling 指标类，例如 `rSMA`、`rATR`、`rMACD`。
- `params`：传给 pyta2 指标构造函数的参数，使用真实参数名。
- `bind`：把 `forward()` 参数绑定到数据路径。
- `namespace`：feature 输出所在命名空间，默认 `feature`，用于内部 feature 路径分组。
- `extra_window`：传给 pyta2 指标实例，用于扩大真实窗口。
- `outputs`：可选输出重命名规则。默认从 pyta2 `output_keys` 推导。

### SMA

```python
FeatureSpec(
    name="sma10_close",
    cls=rSMA,
    params={"n": 10},
    bind={"values": "kline.close"},
)
```

这会实例化：

```python
rSMA(n=10, return_dict=True)
```

并校验：

```python
rSMA.forward(values)
```

### ATR

```python
FeatureSpec(
    name="atr14",
    cls=rATR,
    params={"n": 14, "ma_type": "EMA"},
    bind={
        "highs": "kline.high",
        "lows": "kline.low",
        "closes": "kline.close",
    },
)
```

这会实例化：

```python
rATR(n=14, ma_type="EMA", return_dict=True)
```

并校验：

```python
rATR.forward(highs, lows, closes)
```

### MACD

```python
FeatureSpec(
    name="macd_close",
    cls=rMACD,
    params={"n1": 26, "n2": 12, "n3": 9},
    bind={"values": "kline.close"},
)
```

这会实例化：

```python
rMACD(n1=26, n2=12, n3=9, return_dict=True)
```

并得到 pyta2 输出键：

```python
["dif", "dea", "macd"]
```

默认输出列：

```python
[
    "macd_close_dif",
    "macd_close_dea",
    "macd_close_macd",
]
```

## 输出命名规则

sigma 不复制 pyta2 schema，但需要负责 ML 矩阵列名。

规则：

1. 单输出指标默认输出列名等于 `FeatureSpec.name`。
2. 多输出指标默认输出列名为 `{FeatureSpec.name}_{output_key}`。
3. 用户可以通过 `outputs` 显式重命名。
4. `outputs` 为字符串时只允许用于单输出指标。
5. `outputs` 为字典时 key 必须完整覆盖 pyta2 `output_keys`。

单输出：

```python
FeatureSpec(
    name="sma10_close",
    cls=rSMA,
    params={"n": 10},
    bind={"values": "kline.close"},
)
```

pyta2 输出键：

```python
["ma"]
```

sigma 输出列：

```python
["sma10_close"]
```

多输出：

```python
FeatureSpec(
    name="macd_close",
    cls=rMACD,
    params={"n1": 26, "n2": 12, "n3": 9},
    bind={"values": "kline.close"},
)
```

pyta2 输出键：

```python
["dif", "dea", "macd"]
```

sigma 输出列：

```python
["macd_close_dif", "macd_close_dea", "macd_close_macd"]
```

显式重命名：

```python
FeatureSpec(
    name="macd_close",
    cls=rMACD,
    params={"n1": 26, "n2": 12, "n3": 9},
    bind={"values": "kline.close"},
    outputs={
        "dif": "macd_dif_12_26",
        "dea": "macd_dea_9",
        "macd": "macd_hist",
    },
)
```

## 输入绑定规则

`bind` 的 key 必须对应 `forward()` 的参数名。

例如：

```python
rSMA.forward(values)
```

对应：

```python
bind={"values": "kline.close"}
```

```python
rATR.forward(highs, lows, closes)
```

对应：

```python
bind={
    "highs": "kline.high",
    "lows": "kline.low",
    "closes": "kline.close",
}
```

如果缺少 key 或出现未知 key，sigma 应该在 engine 初始化时直接报错，而不是运行到实时行情中才失败。

## 数据路径

sigma 的数据路径分为两类。

外部行情路径：

```python
kline.open
kline.high
kline.low
kline.close
kline.volume
orderbook.bid_price_1
orderbook.ask_price_1
trades.price
trades.volume
```

内部 feature 路径：

```python
feature.sma10_close
feature.sma10_close.ma
feature.macd_close.dif
feature.macd_close.dea
feature.macd_close.macd
```

固定的 `feature` 前缀信息量有限，因此 `FeatureSpec` 提供 `namespace` 字段。默认 namespace 是 `feature`，用户也可以按业务语义分组：

```python
alpha.sma10_close
alpha.sma10_close.ma
alpha.macd_close.dif
trend.sma20_close
micro.spread_bid1_ask1
label.ret_5
```

规范路径使用 pyta2 原始输出键作为末级字段：

```python
<namespace>.<feature_name>.<output_key>
```

单输出 feature 可以额外提供短路径别名，例如 `alpha.sma10_close` 等价于 `alpha.sma10_close.ma`。多输出 feature 必须显式指定输出键，例如 `alpha.macd_close.dif`。

内部路径不应该使用用户重命名后的输出列名。即使用户把 `macd_close.dif` 输出列重命名为 `macd_dif_12_26`，组合 feature 仍然绑定：

```python
alpha.macd_close.dif
```

## 组合 feature

sigma 必须支持基于 pyta2 指标输出再计算新 feature。

例如先计算 MACD：

```python
FeatureSpec(
    name="macd_close",
    cls=rMACD,
    params={"n1": 26, "n2": 12, "n3": 9},
    bind={"values": "kline.close"},
)
```

再对 `dif` 计算 SMA：

```python
FeatureSpec(
    name="sma10_macd_dif",
    cls=rSMA,
    params={"n": 10},
    bind={"values": "alpha.macd_close.dif"},
    namespace="alpha",
)
```

这要求 sigma 执行器具备 feature DAG 能力：

1. 解析每个 `bind` 的依赖路径。
2. 区分外部行情依赖和内部 feature 依赖。
3. 对内部 feature 依赖做拓扑排序。
4. 实时模式下按拓扑顺序逐个更新节点。
5. 批量模式下用同一套顺序 replay 历史数据。

## 组合 feature 的窗口

单个 pyta2 节点的结构窗口来自：

```python
obj.required_window
```

`required_window` 不等于“第一个有效非 NaN 输出”。`rIndicator` 的设计要求子类自行决定点数不足时返回什么。sigma 的核心职责是计算和按时间对齐输出，不负责样本裁剪。因此这里需要区分：

- `required_window`：单个 pyta2 实例声明的输入窗口长度。
- `effective_required_window`：组合 feature 沿 DAG 传播后的结构窗口。
- `first_valid_index`：训练数据后处理层可选计算的第一次有效位置，不属于 sigma 核心裁剪策略。

组合 feature 的结构窗口需要沿 DAG 传播。

例如：

```python
macd_close.required_window = 34
sma10_macd_dif.required_window = 10
```

`sma10_macd_dif` 第一个有效输出不能只看自己的 10 个输入点，因为它依赖的 `macd_close.dif` 本身要先 warmup。

保守推导：

```python
effective_required_window =
    upstream_effective_required_window + current_required_window - 1
```

因此：

```python
sma10_macd_dif.effective_required_window = 34 + 10 - 1
```

如果多个输入依赖不同上游节点，取最大上游 warmup：

```python
effective_required_window =
    max(upstream_effective_required_window) + current_required_window - 1
```

外部行情路径的 upstream warmup 视为 1。

这个公式只用于 buffer 分配和保守 warmup 估计。engine 应保留完整时间序列输出，让指标自然返回 NaN 或其它无效值。是否 drop warmup、按 `first_valid_index` 裁剪、构造训练样本，是 ML 数据集构建层的后处理职责。

## FeatureEngine

`FeatureEngine` 是执行层。

```python
engine = FeatureEngine(features)
```

初始化时做：

1. 实例化每个 pyta2 指标对象。
2. 读取 `output_keys`、`required_window`、`schema`、`meta_info`。
3. 通过 `forward()` 签名校验 `bind`。
4. 构建 feature DAG。
5. 计算每个外部输入路径需要的最大 buffer 长度。
6. 计算每个内部 feature 输出路径需要的最大 buffer 长度。

实时模式：

```python
engine.update(
    kline={
        "open": 101.0,
        "high": 103.0,
        "low": 100.0,
        "close": 102.0,
        "volume": 1200.0,
    }
)

row = engine.latest()
```

批量模式：

```python
matrix = engine.batch(
    data={
        "kline": kline_df,
    },
)
```

批量模式和实时模式应该共享同一个执行逻辑。批量只是把历史数据逐行 replay 到 engine，并返回与输入时间轴对齐的完整输出。未来如需性能优化，可以对无内部依赖的简单 feature 使用 pyta2 原有 batch 函数，但优化结果必须和 rolling replay 对齐。

## Buffer 设计

sigma 应按数据路径共享 buffer。

例如：

```python
FeatureSpec(
    name="sma10_close",
    cls=rSMA,
    params={"n": 10},
    bind={"values": "kline.close"},
)

FeatureSpec(
    name="sma20_close",
    cls=rSMA,
    params={"n": 20},
    bind={"values": "kline.close"},
)
```

只需要一个：

```python
kline.close
```

buffer 长度取最大需求：

```python
max(10, 20)
```

如果还有：

```python
FeatureSpec(
    name="sma10_macd_dif",
    cls=rSMA,
    params={"n": 10},
    bind={"values": "alpha.macd_close.dif"},
    namespace="alpha",
)
```

则需要为内部路径建立 buffer：

```python
alpha.macd_close.dif
```

这个内部 buffer 的长度至少满足下游节点需求。

实现上可以使用类似 `DequeTable` 的结构统一管理多字段 buffer：

```python
external_buffers = DequeTable(...)
feature_buffers = DequeTable(...)
```

但这是 sigma 的内部实现细节，不应该暴露到用户 API。

## Pyta2Adapter

`Pyta2Adapter` 是非常薄的一层，不是完整 `IndicatorDef`。

职责：

1. 根据 `FeatureSpec.cls` 和 `FeatureSpec.params` 实例化 pyta2 指标。
2. 传入 `extra_window`、`return_dict=True` 和明确的输出缓存大小。
3. 读取 pyta2 实例上的输出和窗口元信息。
4. 校验 `bind` 和 `forward()` 签名。
5. 把路径 buffer 转换成 `forward()` 需要的参数。
6. 调用 `obj.rolling(**inputs)`。
7. 把 pyta2 输出 dict 映射为 sigma feature 输出列。

当前 `rIndicator` 默认会创建只保留最近一条记录的 `_outputs`。`buffer_size > 0` 表示有限缓存，`buffer_size=0` 或 `None` 表示关闭缓存，`buffer_size=-1` 表示无限缓存。sigma 自己会维护 feature buffer，因此 adapter 可以明确传入：

```python
buffer_size=1
```

伪代码：

```python
class Pyta2Adapter:
    def __init__(self, spec: FeatureSpec):
        self.spec = spec
        self.obj = spec.cls(
            **spec.params,
            extra_window=spec.extra_window,
            buffer_size=1,
            return_dict=True,
        )
        self.input_keys = inspect_forward_inputs(self.obj.forward)
        self.output_keys = self.obj.output_keys
        self.required_window = self.obj.required_window
        validate_bind(self.input_keys, spec.bind)

    def rolling(self, buffers):
        kwargs = {
            key: buffers[path].values
            for key, path in self.spec.bind.items()
        }
        output = self.obj.rolling(**kwargs)
        return map_outputs(self.spec, self.output_keys, output)
```

## 用户友好 DSL

底层 `FeatureSpec` 使用 pyta2 的真实参数名，但用户日常不一定需要直接写。

可以提供 DSL：

```python
features = [

    ATR(window=14),

```

展开为：

```python
FeatureSpec(

    cls=rSMA,
    params={"n": 10},
    bind={"values": "kline.close"},
)
```

```python
FeatureSpec(
    name="atr14",
    cls=rATR,
    params={"n": 14, "ma_type": "EMA"},
    bind={
        "highs": "kline.high",
        "lows": "kline.low",
        "closes": "kline.close",
    },

```

```python
FeatureSpec(
    name="macd_close",
    cls=rMACD,
    params={"n1": 26, "n2": 12, "n3": 9},
    bind={"values": "kline.close"},

```

也可以显式写组合 feature：

```python
features = [
```

## ML 批量生成

ML 场景推荐先生成 `FeatureSpec`，再交给 engine。

```python
features = []

for n in [5, 10, 20, 60]:
    for field in ["open", "high", "low", "close", "volume"]:
        features.append(
            FeatureSpec(
                name=f"sma{n}_{field}",
                cls=rSMA,
                params={"n": n},
                bind={"values": f"kline.{field}"},
            )
        )

features.append(
    FeatureSpec(
        name="atr14",
        cls=rATR,
        params={"n": 14, "ma_type": "EMA"},
        bind={
            "highs": "kline.high",
            "lows": "kline.low",
            "closes": "kline.close",
        },
    )
)

features.append(
    FeatureSpec(
        name="macd_close",
        cls=rMACD,
        params={"n1": 26, "n2": 12, "n3": 9},
        bind={"values": "kline.close"},
        namespace="alpha",
    )
)

features.append(
    FeatureSpec(
        name="sma10_macd_dif",
        cls=rSMA,
        params={"n": 10},
        bind={"values": "alpha.macd_close.dif"},
        namespace="alpha",
    )
)
```

优点：

- pyta2 指标元信息不重复维护。
- 参数是 dict，方便网格搜索、去重、序列化。
- 输入路径明确，支持 kline、orderbook、trades 和内部 feature。
- 输出列名稳定，适合直接进入训练矩阵。
- batch 和 rolling 使用同一份 feature 声明。

## 与 pyta2 batch API 的关系

`pyta2` 当前已有类似：

```python
SMA(values, n)
ATR(highs, lows, closes, n, ma_type)
MACD(values, n1, n2, n3)
```

这类 batch API 基于 `forward_rolling_apply`，适合单个指标的批量 replay。

sigma 的 batch engine 不应该简单拼接这些 batch 函数，因为 sigma 还需要处理：

- 多 feature 共享输入 buffer
- 内部 feature 依赖
- 多输出 feature 的列名映射
- 外部行情源和内部 feature 路径混合
- batch 与 rolling 语义完全一致

因此，sigma 的默认 batch 实现应使用 `FeatureEngine` replay。后续可以针对无依赖子图做优化，但优化必须通过一致性测试：

```python
engine.batch(history) == replay(engine.update(row) for row in history)
```

## pyta2 可能需要的小改进

v3 不要求立即修改 pyta2，但从 sigma 集成角度看，有几个小改进会降低适配成本。

### 显式 input_keys

当前 sigma 可以通过 `inspect.signature(obj.forward)` 得到输入名。

未来可以在 `rIndicator` 子类上增加可选类属性：

```python
input_keys = ("values",)
```

或：

```python
input_keys = ("highs", "lows", "closes")
```

这不是必须项，但能避免动态 inspect，也能让文档和工具更稳定。

### 可关闭输出缓存

`rIndicator` 当前会维护 `_outputs`。sigma 自己也会维护 feature matrix 和 feature buffers，可能出现双重缓存。

现在可以使用 `buffer_size=0` 表达“关闭缓存”；`buffer_size=None` 作为兼容别名：

```python
buffer_size=0
```

关闭缓存时 `outputs` 为 `None`，指标仍然返回正常的 rolling 结果。`buffer_size=-1` 表示无限缓存，应谨慎使用。

在 sigma adapter 中，应使用：

```python
buffer_size=1
```

这样 sigma rolling 场景可以只保留自己需要的共享 buffer。

### meta_info 增加输入签名

当前 `meta_info` 已经包含 `name`、`full_name`、`schema`、`window`、`extra_window`、`required_window` 等信息。

未来可以增加：

```python
"input_keys": ("values",)
```

这样 sigma adapter 可以完全基于实例元信息工作。

## v2 到 v3 的变化

v2：

- 引入完整 `IndicatorDef`
- 在 sigma registry 中维护输入、输出、窗口参数
- 使用 `params={"window": 10}` 作为底层示例

v3：

- 删除完整 `IndicatorDef`
- pyta2 实例是指标定义事实来源
- sigma 只维护 `FeatureSpec` 和执行图
- 输出键从 `obj.output_keys` 读取
- 窗口从 `obj.required_window` 读取
- 低层 `params` 使用真实 pyta2 构造参数，例如 `{"n": 10}`、`{"n1": 26, "n2": 12, "n3": 9}`
- 高层 DSL 可以继续提供 `window`、`fast`、`slow`、`signal` 等友好别名
- 增加内部 feature 路径和组合 feature DAG

## 结论

推荐 v3 作为后续方向：

1. `pyta2` 保持指标内核定位，并作为指标元信息事实来源。
2. sigma 不重复定义 output/schema/window，只负责数据路径绑定和 feature 编排。
3. `FeatureSpec` 使用 pyta2 真实构造参数，保证可复现。
4. 用户 DSL 可以提供更友好的参数别名，但必须展开到稳定的 `FeatureSpec`。
5. sigma 的核心能力应包括 feature DAG，这样才能支持“指标的指标”和复杂 ML 特征。
6. batch 与 rolling 使用同一套 engine 语义，性能优化后置。
